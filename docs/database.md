# SQLite: каталог запитань

Обрана SQLite: один локальний файл і SQL-запити без окремого сервера баз даних. Це відповідає [рекомендованим сценаріям SQLite](https://www.sqlite.org/whentouse.html) для локального сховища. При багатьох незалежних серверних записувачах слід переглянути вибір.

Редаговані матеріали: [CSV](../content/questions.uk.csv). Go перевіряє їх та імпортує в SQLite транзакцією. [SQL-схема](../server/internal/catalog/schema.sql) містить категорії, раунди, запитання й метадані набору. Неправильні дані не стирають попередній набір. API читає метадані та запитання в одному snapshot.

У Git зберігаються CSV, схема та код; база `.local/data/quiz.sqlite` і її журнали ігноруються. Після зміни CSV потрібно повторити імпорт. Для production імпорт вимагає 152 затверджені позиції у визначених 18 раундах. Наявний CSV — авторська чернетка, тому production gate її відхиляє.

Go використовує `database/sql` і [modernc.org/sqlite](https://pkg.go.dev/modernc.org/sqlite) без окремої C-збірки. Пакети завантажуються у проєктний кеш через [env.ps1](../scripts/env.ps1). SQLite CLI і графічна програма перегляду не потрібні для запуску.

Flutter використовує [Drift](https://pub.dev/packages/drift) поверх SQLite зі спільною схемою для мобільних платформ і браузера. Клієнтська схема версії 2 містить `settings`, `round_progress_entries`, `attempts` і `content_snapshots`. Збереження завершеної спроби транзакційно додає історію та оновлює останній/найкращий результат. Новий API snapshot спочатку проходить перевірку контракту, а потім атомарно замінює попередній; пошкоджене оновлення залишає робочу копію.

Для вебу додані [WASM і worker](https://drift.simonbinder.eu/platforms/web/) з офіційного Drift 2.35.4. Go-сервер віддає `Cross-Origin-Opener-Policy` і `Cross-Origin-Embedder-Policy`, тому сумісний браузер може використовувати постійне OPFS-сховище; Drift має IndexedDB fallback. Очищення браузерних даних видаляє локальний прогрес. Go-база та клієнтські бази — різні файли, обмін лише через API.

Міграції серверної схеми починаються з `PRAGMA user_version=1`. Майбутню зміну схеми додавати як нову версію з тестом переходу зі старої. Резервну копію робити після закриття всіх з’єднань або через SQLite backup API; після відновлення перевірити цілісність і кількості запитань.

Клієнтська міграція 1 → 2 додає звук, вібрацію, історію спроб і кеш контенту без втрати наявних налаштувань/прогресу. Після зміни Drift-таблиць виконати `scripts/generate-drift.ps1`, закомітити оновлений `local_database.g.dart` і додати тест переходу з попередньої схеми.
